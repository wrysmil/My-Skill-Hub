# 🔨 03-build — 做出 MVP，一个能验证假设的东西

> **要回答的问题：怎么在最短时间内做出一个能验证假设的东西，而不是一个半成品？**

## 什么时候进入

- 当你手里有一份写好的实施计划，可以直接照着推进的时候。
- 当功能列表在膨胀，你不确定第一版到底该砍到只剩什么的时候。
- 当你准备实现任何功能或修复任何 bug，需要先建立测试防护的时候。
- 当你要给项目定下分支模型、提交规范与合并流程的时候。
- 当你要设计面向 Agent 的提示词与自定义指令，或者构建多组件、有状态与路由的复杂前端产物时。

## 什么时候不该进入

- 计划还没写 —— 在没有计划的情况下开工，等于把设计决策推迟到写代码时做，成本最高，先回 `02-design`。
- 需求本身还没验证 —— 先确认你要做的东西值得做，回 `01-discover`。

## 产出物

- 一个能跑通核心闭环的可部署版本，而不只是"功能都写完了"。
- 一条可回滚的提交历史，每次提交都能说明做了什么、为什么。
- 一份覆盖核心路径的测试，以及它在 CI 或本地可重复跑通的记录。
- 一份写进计划文件的上线前 checklist，逐项已勾选。

## 技能

| 技能 | 什么时候用它 |
| --- | --- |
| [`mvp-scoping`](mvp-scoping/) | 功能列表在膨胀、不确定第一版该砍到只剩什么时 |
| [`test-driven-development`](test-driven-development/) | 实现任何功能或修 bug 之前 |
| [`executing-plans`](executing-plans/) | 有书面计划要分阶段推进并设置检查点时 |
| [`git`](git/) | 需要分支模型、提交规范、合并流程时 |
| [`logging-standards`](logging-standards/) | 要写或审查日志代码时 |
| [`prompt-engineering-expert`](prompt-engineering-expert/) | 要设计给 Agent 用的提示词与自定义指令时 |
| [`web-artifacts-builder`](web-artifacts-builder/) | 要做多组件、有状态与路由的复杂前端产物时 |

## 常见反模式

**「功能都做完了再上线」** → 上线拖得越久，你离"假设被验证"越远，做的大部分功能可能根本没人用。

**「先欠着技术债，以后重构」** → 你能验证假设之前项目可能已经死了，"以后"通常不会来，债会先变成改不动的代码。

**「MVP 就是功能的子集」** → MVP 是"最小可验证闭环"，砍掉的是功能，不能砍掉闭环 —— 用户走不完这条路就等于没做。

**「测试等有用户了再补」** → 没有测试你连"改完还是对的"都无法确认，补测试的成本比一开始写高得多。

## 下一步

当核心闭环能在真实环境跑通、且你有办法观察到用户行为时，进入 `04-verify`。如果实现过程中发现计划里的某个关键假设在技术上不成立（比如依赖的接口根本拿不到数据），应该回退到 `02-design` 重新设计，而不是用临时补丁绕过。
