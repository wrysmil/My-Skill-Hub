# 🛠 06-operate — 让它一直活着，出了事能收拾

> **要回答的问题：系统上线之后靠什么持续活着？出故障、被入侵、被要求合规时，第一步做什么？**

## 什么时候进入

- 当系统已经在生产环境跑着，用户在用，你开始要为「它半夜挂了」负责的时候。
- 当有人报「服务器连不上了」「数据库连不上了」「网站打不开了」，而你需要先定位再动手的时候。
- 当你要定备份策略、做恢复演练，或者被问到「备份能不能真的恢复」的时候。
- 当怀疑被入侵、数据可能泄露，你需要知道**先取证还是先处置**的时候。
- 当要做安全基线检查、漏洞修补、等保/数据合规自查，或者要给出一份审计报告的时候。
- 当日常巡检、日志告警、根因分析开始重复，需要固化成自动化脚本的时候。

## 什么时候不该进入

- 系统还没上线、核心闭环还没验证 —— 先回 `03-build` 或 `04-verify`，给一个没人用的东西做运维体系是纯浪费。
- 你要做的是架构设计层面的选型（该用哪个数据库、怎么分层）—— 那是 `02-design`。
- 你要定位的是**自己写的代码**里的 bug、测试失败、偶发异常 —— 那是 `04-verify/systematic-debugging`，工具与思路完全不同。
- 你只是想把「运维很重要」写进方案文档去说服别人 —— 这里给的是可执行命令与检查单，不是论证材料。

## 产出物

- 一份**只读诊断**得出的根因判断：现象、证据、影响面、下一步动作，而不是"重启试试"。
- 一套可验证的备份与回滚方案：备份存放位置、保留周期、恢复步骤，以及一次真的跑过的恢复演练记录。
- 一份安全基线检查单：逐项核对结果 + 不符合项的修补方案。
- 应急响应时的**证据保全快照**与处置时间线：谁在什么时候做了什么，为什么。
- 一份可以交给下一个人执行的巡检清单或自动化脚本。

| 技能 | 什么时候用它 |
| --- | --- |
| [`it-ops-personal`](it-ops-personal/) | 服务器/数据库故障排查、安全加固、备份恢复、监控日志、应急响应与溯源、安全基线与数据合规自查 |

## 常见反模式

**「先重启试试，说不定就好了」** → 重启会清掉内存里的进程、连接、临时文件，也就是**清掉证据**。故障和入侵的根因经常只存在于重启前的那几分钟里。先采样，再动手。

**「日志先清理干净，看着乱」** → 在应急响应里清日志等于销毁证据，也可能让你错过横向移动的痕迹。日志该做的是归档、轮转、异地留存，不是删除。

**「我们有备份」** → 没做过恢复演练的备份不算备份，只是"一份不知道能不能用的数据"。真出事时才发现备份是空的、或者缺了半年前的 schema 变更，代价是灾难级的。

**「漏洞先放着，等下次发版一起修」** → 高危漏洞的利用窗口以小时计，不是以发版周期计。分级之后该热修的热修，该临时缓解的先缓解。

**「生产上直接改，改坏了再回滚」** → 没有事先验证过的回滚方案，等于没有回滚方案。变更前明确备份点、验证方式、回滚路径，这三样缺一不动手。

**「等保/合规就是填表」** → 表格背后是密码策略、权限最小化、日志留存这些实际控制项。只填表不落地，检查过不了，出了事也兜不住。

## 下一步

运维不是终点，是一个持续循环：巡检发现的问题回流成 `02-design` 的改进项，反复出现的故障模式应该固化成监控规则或自动化脚本，而每一次事故复盘产出的教训值得沉淀成技能（`00-meta/skill-creator`）。如果运维过程中反复遇到同类判断，说明该把它写成检查单，而不是每次靠人回忆。
