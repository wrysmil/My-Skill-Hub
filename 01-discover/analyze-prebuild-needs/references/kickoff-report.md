# 报告骨架与视频案例

## 开工前需求痛点分析

从结论开始。按材料多少压缩报告，缺口集中放在验证计划里。

| 内容 | 推荐字段 |
| --- | --- |
| 开工建议 | 结论、证据和前提、下一步 |
| 业务边界 | 目标、主品类及理由、关键角色、现有工具或做法、优先跑通的业务流程 |
| 证据台账 | E 编号、来源与时间或版本、原始观察、局限 |
| 痛点清单 | P 编号、角色与场景、卡点与临时做法、影响与频次、证据编号、确定程度及优先理由 |
| 一期需求 | R 编号、关联 P 和 C 或明确约束、来源及确认状态、业务规则、验收标准及状态、一期或后续 |
| 验收指标 | 指标定义、当前基线、期望结果、测量方式。基线缺失时写待测和测法 |
| 验证计划 | 假设、取证对象和方法、确认或推翻的条件、影响的决策 |
| 复用评估 | 仅在影响决策时加入。检索平台、实际查询和日期、候选仓库及版本、许可证和部署约束、能力 C 和关键用例、覆盖判断及来源位置、差距与验证动作 |

## 视频案例

Park的AI笔记以在线课程平台演示系统设计前的四层工作。时间点来自抖音章节，具体细节以演示画面为依据。 [《AI做在线课程平台，先把业务理解对》](https://www.douyin.com/video/7709696478389832994)

| 视频时间 | 演示内容 | 可复用的方法 |
| --- | --- | --- |
| 00:15 | 将在线课程平台的主品类判断为学习管理系统（LMS） | 用用户要完成的任务界定主品类，再看相邻品类 |
| 00:25 | 列出课程与课件、注册选课与权限、进度跟踪、测验考试、作业发布与提交批改、讨论互动、成绩与学习记录、证书或完成证明 | 将业务拆成能逐项检查的能力，按项目证据确定哪些属于一期 |
| 00:42 | 搜索候选开源 LMS，画面出现 Chamilo 和 Frappe LMS，并展示按八项能力逐条对照 README 的过程。Chamilo 演示为七项具备、一项部分具备，注册选课与权限需要进一步核实 | 用品类和关键能力主动找候选，再给每条覆盖判断保留依据，优先验证会卡住业务流程的差距 |
| 01:16 | 把简体中文界面、演示数据、删除权限和存量账号切换等条目写入业务方案，保留依据和确认状态 | 将功能、角色及权限、流程和状态等条目与原始材料或用户决定关联，保留确认状态 |

视频中的项目覆盖率属于当时的演示结果。实际选型按目标版本、部署条件和关键业务用例重新核对。

## 底座证据如何影响开工

假设发起方明确要求角色权限。某候选版本的 README 只写了个人资料编辑。记录该需求为「用户决定／已确认」，把授权规则标为「待核实」、验收标为「待验收」。先澄清角色、允许和禁止的操作，再用目标版本验证正反两类用例。若验证后还无法满足必需权限，把修补或更换底座列为开工条件。

## 痛点到需求示例

以下是用于演示写法的假设，不是视频中的用户调研。

- **P1 假设**：讲师在周作业截止后，要从群聊下载文件，再逐个比对名单，才能找出漏交学员。耗时和漏判次数待测。
- **验证动作**：跟讲师复盘最近一次催交，对照群文件与班级名单，记录核对步骤和耗时。若重复核对造成可观察的时间成本或漏判，就试点作业提交状态查询。若困难来自通知没有送达，则优先验证通知流程。
- **C1 → R1 候选**：按课程名单查询作业提交状态。若进入一期，用一组包含已交、补交、未交的真实脱敏样例验收，检查讲师能否找出正确名单，以及核对时间是否改善。
