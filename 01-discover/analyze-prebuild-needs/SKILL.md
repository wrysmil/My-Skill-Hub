# 系统开工前需求痛点分析

把系统提议还原成业务问题，形成可追溯的需求和开工建议。以目标用户完成关键任务的实际结果来判断系统价值。

## 1. 界定业务与分析边界

先用已有材料描述业务目标、使用者和受影响角色、触发场景、期望结果、现有系统及明确约束。提出主品类及判断理由。相邻品类会改变一期范围时，说明两者分别服务的核心任务和区分依据。品类用来发现遗漏，实际范围以业务证据和明确约束为准。

## 2. 还原现状并验证痛点

- 找一个最近发生的实际案例，串起触发、角色、操作、交接、关键异常和结果。优先复用已有访谈、工单、流程记录、样表或日志。关注用户目前怎样绕过问题，以及绕过的代价。
- 每个痛点写清楚**哪个角色在什么条件下做什么，卡在哪一步，用什么办法补救，造成什么后果**。给出频次、影响和观察口径，有数据就注明来源和样本范围。原因待查时写成假设，并说明什么证据会推翻它。
- 证据条目用 E 编号，记录来源、时间或版本、观察及局限。区分观察事实、用户反馈或明确决定、分析推断和待验证事项。把未经证实的事件记录为反馈线索，用亲历者或业务记录核实事件、频次和影响。竞品和 README 只作为品类或实现证据。
- 若缺关键材料，先交付有用的初稿，再指出最能改变结论的证据缺口。给一个低成本验证动作，写明找谁、看哪段流程或记录、出现什么结果就推进或调整。缺失的频次、耗时和目标标成待测或待定。

## 3. 拆业务能力，拟定一期范围

- 沿着关键业务流程拆出能力，用品类常见能力查漏，逐项判断是否服务于当前痛点或约束。给痛点 P、能力 C 和需求 R 编号。每条一期候选需求追溯到证据或明确约束，注明角色、触发条件、规则和可观察的验收结果。把相关异常、权限和存量数据纳入验收。
- 逐条写明需求来自原始材料、用户决定或分析建议，并分别记录确认状态（已确认／待确认）和验收状态（待验收／已通过／未通过）。用户确认的依据可追溯到确认记录，验收通过须有实际结果。
- 结合影响、频次、证据强度、现有替代方式和实施成本取舍。低频高后果的故障可优先处理，说明后果和依据。证据薄弱的高潜力项进入验证清单。对证据充分的需求，选能跑通并验收的最小业务闭环，明确后续项。
- 比较沿用现状、调整流程、复用既有工具和开发中与当前决策有关的路径。

## 4. 主动发现并验证开源底座

开源复用可能影响一期范围或成本时，即使用户没给项目名，也从**业务主品类 + 核心能力或部署约束**出发，在 GitHub 等代码托管平台和项目官网查找候选。例如，自托管课程平台可搜 `open source self-hosted LMS assignments enrollment`。用户指定唯一候选时可直接核对。记录实际查询、检索平台和日期，保留少量候选及仓库链接、目标版本、许可证、维护和部署情况。找不到符合硬约束的项目时，列出落选原因和检索边界。检索受阻时，注明未完成的核验。

按一期候选需求的关键用例逐项对照目标版本的 README、官方文档、源码或试验结果，标为具备、部分具备、不具备或待核实。每项附章节链接、源码路径或试验记录，注明已覆盖的规则、缺口和适配成本。只有功能名称或没有文档证据时，用源码或小范围试验补证，暂无法核实则保留待核实。

把结果回写到一期范围、实现路径和验收用例。必需能力的缺口用验证、二开或替代底座解决。缺口仍未解决时，列为开工条件，保留原需求及其确认状态。

## 5. 给出开工建议

先说明建议适用于哪个方案或哪部分工作，再给推进条件。

- **可开工**：已有核心流程的证据，一期需求有已验证痛点或明确约束支撑，验收标准明确，关键依赖和硬约束具备可行路径。
- **先试点**：问题有依据，剩余疑问可用可逆的小范围试验解决。试点也须满足适用于该试点的硬约束。说明它能验证的范围，例如合成数据可用于流程演练，生产部署与真实数据迁移需各自取证。
- **先验证**：关键痛点、约束的可行性或依赖状态仍待核实。先给出能改变决策的取证动作。
- **暂缓**：已有证据显示收益有限或当前方案违反硬约束。说明恢复条件，例如找到可满足约束的替代方案。

默认在对话交付《开工前需求痛点分析》。用户要求沉淀文件时，用项目既有文档位置和格式。需要标准报告结构或想参考在线课程案例时，读 [报告骨架与视频案例](references/kickoff-report.md)。
