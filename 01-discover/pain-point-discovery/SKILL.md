# 痛点发现与验证

## 这个技能解决什么

**核心原则：唯一有效的需求证据是已经发生的行为 —— 花过的时间、花过的钱、找过的替代方案。对未来的口头承诺不是证据。**

技术人最常见的死法不是写不出代码，而是为一个不存在的问题写了三个月代码。这个技能的唯一目标，是在写第一行代码之前，把「我觉得有需求」变成「我手上有他昨天的行为记录」。

## 触发条件

- 有人说「我问了 N 个人，都说会用」
- 样本全部来自熟人、同事、社群
- 你能感觉到对方其实已经决定要做了，只是在找认可
- 需要设计用户访谈提纲
- 要判断一个想法该继续投入还是砍掉

## 不适用

- 需求已经由付费客户用合同或预付款确认了 —— 那是在做交付，不是在做验证
- 纯粹的内部工具，用户就是你自己 —— 那你自己的行为就是证据，直接做

## 四道门槛，不是一道

把「验证通过」当成一个开关，是最大的认知错误。从口头认可到真实付费之间有四道**独立**的门槛，每道都会滤掉大部分样本：

| 门槛 | 你在测什么 | 典型通过率 |
| --- | --- | --- |
| 1. 口头认可 | 「这想法不错」 | 高（社交成本为零，说"会"最礼貌） |
| 2. 真实行为 | 他现在就在用某种笨办法解决 | 中 |
| 3. 持续使用 | 两周后他还在用 | 低 |
| 4. 愿意付钱 | 他掏了钱 | 很低 |

**跨门槛不能推断。** 「8/10 说想用」只证明了门槛 1，它对门槛 4 的预测能力接近于零。

## 核心流程

### 第一步：先问「他现在怎么办」，不要问「他会不会用」

过去的、可验证的行为，价值远高于未来的意愿。

| ❌ 不要问 | ✅ 要问 |
| --- | --- |
| 你会用这个工具吗？ | 你上周具体是怎么处理这件事的？ |
| 你觉得这个需求痛吗？ | 这件事上周占了你多少时间？ |
| 如果有这个功能你会用吗？ | 你为它花过钱吗？花了多少？试过什么工具？为什么不满意？ |
| 这个功能对你有用吗？ | 如果明天现在这个办法不能用了，你会怎么办？ |

**五个杀手问题**（问不出具体答案就说明没有真需求）：

1. 你上一次遇到这个问题是什么时候？（说不出具体时间 = 不痛）
2. 你现在怎么解决的？（「忍着」= 痛度不够；「用 Excel + 手动」= 真痛）
3. 你为它花了多少钱、多少时间？（有数字 = 真痛）
4. 你试过别的工具吗？为什么放弃了？（试过并放弃 = 有需求但市场没满足）
5. 如果这东西明天消失，你会怎么办？（「那就回到原样」= 可替代；「那我麻烦了」= 有价值）

### 第二步：把熟人和非熟人分开

**熟人的认可不算数据。** 熟人被问「你会用吗」时，说"会"成本为零，说"不会"要付社交成本。他不是在骗你，他是在对你友好。

- 熟人样本只能用来**发现问题**，不能用来**验证需求**
- 任何结论里，必须单独列出「非熟人样本数」
- 如果非熟人样本 < 5，你没有资格下任何结论

### 第三步：爬承诺阶梯

不要一次索要最大的承诺。让用户**逐级付出越来越高的成本**，看他愿意爬到第几级。停在某一级，就是真实的证据强度。

| 阶梯 | 你索要的东西 | 他付出 | 信号强度 |
| --- | --- | --- | --- |
| 1 | 一句「挺有用的」 | 0 | 无 |
| 2 | 20 分钟访谈 | 时间 | 弱 |
| 3 | 填一份调查表 | 少量时间 | 弱 |
| 4 | 留下微信/邮箱，同意你后续联系 | 联系方式 | 中 |
| 5 | **交出本周真实素材**（他的原始数据） | 隐私 + 时间 | 强 |
| 6 | 每周和你见一次，持续 3 周 | 持续时间 | 强 |
| 7 | **付定金 / 预付款** | 钱 | 决定性 |

**礼宾测试（Concierge Test）** 是这一整套里性价比最高的动作：不写任何代码，你本人手工提供完整服务。比如帮人写周报，就让他把原始素材发你，你手写一版给他。

看四件事：①有几个人**真的把素材发来了**；②他改了多少；③下周他**主动**回来找你吗；④有没有人说「这个别写」。

巅峰是第 6–7 级。**收 1 块钱也远强于 100 句「我要用」。**

### 第四步：写下失败判据

在开始验证**之前**，把「什么结果就放弃」写下来。这是唯一能防止你给自己找证据的办法 —— 人类在一件事上投入之后，会自动开始收集支持自己的信息。

```markdown
## 验证计划：<想法名>      日期：____

目标人群：____（必须排除熟人）

| 动作 | 通过（继续） | 失败（转向或停） |
|---|---|---|
| 承诺阶梯第 5 级：交出真实素材 | N 人里 ≥ M 人交付 | ≤ K 人交付 |
| 礼宾测试第 2 周复购 | ≥ 50% 主动回来 | 无人主动回来 |
| 收费测试 | ≥ 3 人真付款 | 0–1 人付款 |
| 反向提问「明天关了你怎么办」 | 明显焦虑 / 有花钱史 | 「那就接着手写」 |
| 数据授权测试（若需读他的数据） | 多数接受 | 多数拒绝 = 模式不成立 |

**结论约定：以上任意两项失败即停。**
```

### 第五步：产出可证伪的需求假设

验证的产出不是「需求成立」，而是一句**能被证伪的话**：

> ❌ 需求验证通过，可以开工。
> ✅ 「远程团队的程序员，每周至少要花 40 分钟凭记忆拼凑周报，其中 ≥ 60% 的人愿意为此每月付 29 元」—— 如果一个月内收不到 3 笔付款，这句话就是假的。

## Red Flags — 出现这些想法就停下

- 「我朋友都说好」→ 熟人不算样本
- 「8/10 的人都说会用」→ 那只测了第一道门槛
- 「这个需求显而易见，不用验证」→ 显而易见的痛通常已经有现成解法了，正因如此才更需要查
- 「先做出来再说，用户会自己来」→ 这是把验证成本从 1 周推到 3 个月
- 「他们提了这么多建议，说明很有兴趣」→ 提建议成本为零，付钱成本不为零
- 「用户说很想要，只是嫌贵」→ 「嫌贵」通常等于「没价值」，不是价格问题
- 「问了一圈，没人反对」→ 没有反对者说明你在做社交，不是在做调研

**出现任一条：停下，回到第一步。**

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 问意愿不问行为 | 所有问题改成过去时：「上周你是怎么做的」 |
| 只测一道门槛，当成整体通过 | 明确写出当前证据在第几级阶梯 |
| 样本是熟人却说不出样本来源 | 每份记录标注「熟人 / 非熟人」 |
| 访谈问“你需要什么功能” | 问「你雇这个东西来干什么活」（JTBD） |
| 收集完数据再定判据 | 判据必须**先写**，写在数据之前 |
| 把「他愿意试」当成「他会付钱」 | 至少做一次真实收费动作，金额可以很小 |

## 这个技能不负责什么

它只判断「这个痛点是否真实存在、是否有人为它付钱」。**决定砍到多小、先做哪个功能** 属于 `03-build/mvp-scoping`；**上线之后怎么用数据决定去留** 属于 `04-verify/value-validation`。
