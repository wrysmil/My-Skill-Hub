# Memory Bank（记忆库）

一套自适应记忆系统：为 Claude Code 提供跨会话的持久、智能上下文，同时减少令牌浪费，使会话可持续时间延长约 3–5 倍。不是单层扁平文件，而是可压缩、分支化、差异对比、自愈、且只加载关键信息的分层架构。

---

## 核心架构

Memory Bank 分三层运作：

```
┌─────────────────────────────────────────────┐
│  第 2 层：全局记忆                           │
│  ~/.claude/GLOBAL-MEMORY.md                 │
│  跨项目模式、用户偏好、可复用决策。持久保存。 │
├─────────────────────────────────────────────┤
│  第 1 层：项目记忆                           │
│  ./MEMORY.md（+ 分支叠加层）                 │
│  架构、决策、进行中的工作。随项目生命周期存在。 │
├─────────────────────────────────────────────┤
│  第 0 层：会话上下文                         │
│  仅存在于当前对话中。                         │
│  当前任务焦点、临时笔记。                     │
│  会话结束时消失（会刷写到第 1 层）。          │
└─────────────────────────────────────────────┘
```

**第 0 层（会话）** — 临时。记录当下正在做什么。会话结束时自动刷写到第 1 层。

**第 1 层（项目）** — 主记忆文件。记录项目状态、决策、进行中的工作、阻塞项。分支感知：每个 git 分支可有独立叠加层，与基础记忆合并。

**第 2 层（全局）** — 跨项目知识。编码偏好、工具选择、常用模式。位于 `~/.claude/GLOBAL-MEMORY.md`。在会话开始时与第 1 层一并加载。

> 完整架构见 `references/memory-layers.md`。

## 工作流

### 1. 会话开始 — 加载序列

在做其他事之前执行：

```
步骤 1：检测记忆文件（顺序固定：先全局、后项目，避免只读仓库内文件）
  └─ 检查 ~/.claude/GLOBAL-MEMORY.md（Windows：`%USERPROFILE%\.claude\GLOBAL-MEMORY.md`；在工作区外，须主动按绝对路径读取）
  └─ 检查项目根目录是否有 MEMORY.md
  └─ 检查 MEMORY-ARCHIVE.md（是否已归档历史）

步骤 2：检测 git 上下文
  └─ 当前分支名
  └─ 检查 .memory/branches/<分支>.md 叠加层
  └─ 距上次会话天数（来自「最后更新」字段）

步骤 3：会话差异（若可用 git）
  └─ 自上次记忆更新以来的提交
  └─ 自上次会话以来变更的文件
  └─ 记忆与当前代码状态之间的冲突

步骤 4：健康检查
  └─ 为记忆新鲜度打分（见下文「记忆健康度评分」）
  └─ 标出陈旧条目
  └─ 标出记忆中引用但已不存在的文件

步骤 5：上下文感知的问候
  └─ 用 2–3 句具体说明上次停在哪
  └─ 报告检测到的漂移（代码变了、记忆过期等）
  └─ 说明下一步应立即做什么
  └─ 询问：「直接继续，还是计划有变？」
```

**问候示例（记忆新鲜、同一分支）：**
> 欢迎回来！上次你完成了 `src/api/webhooks/stripe.ts` 里的 Stripe webhook 处理，正准备写集成测试。`handlePaymentSuccess()` 已完成，但 `handleRefund()` 仍是桩代码。之后有 3 次提交，都是你自己的，没有意外。要继续写集成测试吗？

**问候示例（记忆陈旧、已换分支）：**
> 欢迎回来！你的记忆是 5 天前在 `main` 上的，但你现在在 `feature/user-profiles`。我找到 3 天前的分支叠加层，里面有头像上传相关上下文。不过记忆中引用的 `src/components/Avatar.tsx` 已改名为 `ProfileImage.tsx`。要继续的话，要不要我先把记忆更新到当前状态？

**若没有 MEMORY.md：**
- 正常继续
- 在完成第一件有意义的工作后，可询问：「要不要我开始记录进度？我会建一个记忆文件，下次会话可以立刻接上。」

---

### 2. 会话中途更新

当用户说「记住这个」或你完成重要里程碑时：

1. 读取当前 `MEMORY.md`
2. 判断变更：
   - 新决策？→ 更新「关键决策」
   - 任务完成？→ 从「进行中」移到「已完成」，更新「上次停在哪」
   - 新阻塞？→ 加入「阻塞项」
   - 重要上下文？→ 加入「备注」
3. 写回更新后的文件
4. 用具体内容确认：「已保存 — 已记录 Zod 迁移决策，并将用户模型标为完成。」

**会话中途不要整文件重写。** 只改变动的区块。这样会话开始时的上下文得以保留。

---

### 3. 会话结束 — 写入序列

收尾时执行完整记忆写入：

```
步骤 1：审计本会话
  └─ 完成了什么？（具体到文件、函数、行）
  └─ 做了哪些决策、原因是什么？
  └─ 什么仍被阻塞或未解决？
  └─ 下一步应做什么？（必须极其清楚）

步骤 2：压缩已完成工作
  └─ 将已完成项移到「已完成」并附一行摘要
  └─ 删除已解决的阻塞
  └─ 归档陈旧备注

步骤 3：更新记忆健康元数据
  └─ 更新「最后更新」时间戳
  └─ 会话计数 +1
  └─ 更新文件引用表（确认路径仍存在）

步骤 4：写入 MEMORY.md
  └─ 用当前状态完整覆盖
  └─ 确认写入成功

步骤 5：检查压缩阈值
  └─ 若超过 150 行，建议压缩
  └─ 若超过 200 行，自动压缩（见「智能压缩」）

步骤 6：提示是否写入全局记忆
  └─ 是否有值得存入第 2 层的跨项目收获？
  └─ 是否发现新的用户偏好？
```

## 分支感知记忆

在多个 git 分支上工作时，记忆会自适应：

```
MEMORY.md                          <- 基础项目记忆（main/主干）
.memory/
  branches/
    feature-auth.md                <- feature/auth 分支叠加层
    feature-payments.md            <- feature/payments 分支叠加层
    bugfix-race-condition.md       <- bugfix 分支叠加层
```

**工作方式：**

1. 会话开始时检测当前 git 分支
2. 先加载基础 `MEMORY.md`
3. 检查 `.memory/branches/<分支 slug>.md` 是否有叠加层
4. 将叠加层合并到基础之上（叠加层区块优先）
5. 会话结束时写回正确层级：
   - 架构决策 → 基础 `MEMORY.md`（跨分支共享）
   - 分支专属工作 → `.memory/branches/<分支>.md`

**分支合并后：**
- 当功能分支合并进 main 时，可提示：
  「`feature/auth` 刚合并。要不要把该分支的记忆叠加层折叠进基础 MEMORY.md 并清理分支文件？」

> 合并策略见 `references/branch-aware-memory.md`。

## 智能压缩

记忆文件会膨胀。智能压缩保持其可用性：

**自动压缩触发：**
- `MEMORY.md` 超过 150 行 → 建议压缩
- 超过 200 行 → 自动压缩
- 超过 5 个会话的旧条目 → 归档候选

**压缩规则：**
1. 超过 3 个会话前完成的任务 → 在会话日志中压成一行
2. 已解决的阻塞 → 完全删除
3. 陈旧的「进行中」项（3+ 会话无进展）→ 向用户标出
4. 决策日志条目 → **绝不压缩**（永久记录）
5. 架构备注 → **绝不压缩**（永久记录）

**归档：**
当会话数超过 10，创建 `MEMORY-ARCHIVE.md`：

```markdown
# 记忆归档
来自项目记忆的已归档会话。

## 会话 1–8 摘要
[早期项目工作的一段摘要]

## 关键里程碑
- 会话 2：初始脚手架完成
- 会话 5：认证系统上线
- 会话 8：数据库迁移至 Prisma 完成
```

> 完整压缩算法见 `references/smart-compression.md`。

## 会话差异对比

会话开始时，检测自上次写入记忆以来发生了什么：

```bash
# 从 MEMORY.md 的「最后更新」字段取日期
# 再检查之后发生的事

git log --oneline --since="[last-updated-date]"
git diff --stat HEAD~[commits-since]
```

**报告格式示例：**
> 自你上次会话（3 天前）以来，共有 7 次提交：你 4 次，同事 @teammate 3 次。主要变更：`src/api/users.ts` 已重构，`package.json` 新增 2 个依赖（zod、@tanstack/query）。你的记忆仍引用 `src/api/users.ts` — 我会核对是否仍准确。

**冲突检测：**
当会话差异显示与记忆矛盾时：
- 记忆写「用 Express」但 `package.json` 已是 Fastify → 标出
- 记忆引用 `src/auth/login.ts` 但文件已删 → 标出
- 记忆写「卡在 API key」但 `.env` 已有 → 更新

> 冲突解决策略见 `references/session-diffing.md`。

## 记忆健康度评分

在 1–10 分范围内，按四个维度为记忆打分：

| 维度 | 权重 | 10 分 | 1 分 |
|------|------|-------|------|
| **新鲜度** | 30% | 今天刚更新 | 超过 14 天未更新 |
| **相关性** | 30% | 引用文件均存在 | 多数文件缺失或已改名 |
| **完整性** | 20% | 各节齐全、下一步清晰 | 缺少关键节 |
| **可执行性** | 20% | 可立刻开工 | 需再问 3 个以上问题 |

**会话开始时展示：**
```
记忆健康度：8/10
  新鲜度：    9/10（昨天更新）
  相关性：    7/10（2 个文件路径已变）
  完整性：    8/10（各节都在）
  可执行性：  9/10（下一步非常清楚）
```

**若健康度 < 5：** 触发恢复模式或建议重建记忆。

## 恢复模式

当记忆严重过期、损坏或缺少关键上下文时：

```
步骤 1：扫描项目
  └─ 读 package.json / pyproject.toml / go.mod（识别栈）
  └─ 读 README.md 与 CLAUDE.md（项目上下文）
  └─ 列出关键目录与最近文件

步骤 2：读 git 历史
  └─ 最近 20 次提交（谁、什么、何时）
  └─ 当前分支与近期分支
  └─ 打开或近期的 PR

步骤 3：重建记忆
  └─ 用 package.json + README 写项目概览
  └─ 用 git 日志中改动最多的文件写关键文件
  └─ 用提交信息与代码模式写关键决策
  └─ 用最近提交写「上次停在哪」
  └─ 标注置信度：「由代码重建 — 请与用户核对」

步骤 4：展示并确认
  └─ 向用户展示重建结果
  └─ 请用户修正
  └─ 写入核对后的 MEMORY.md
```

## 上下文效率引擎

对 Claude Code 的第一大抱怨：**会话太快撞到上下文上限。**
一半令牌花在重复解释上下文，另一半才做实事。Memory Bank 扭转这一比例。

### 令牌问题（经 tiktoken 验证）

没有 memory-bank 时，每次会话开始约消耗 ~1200 令牌：

```
对话开销（4 轮来回）：      ~566 令牌
  用户重新解释项目、栈、状态
  Claude 追问澄清
  用户回答跟进问题
  来回直到 Claude 理解

文件读取（Claude 读 3+ 个文件以建立认知）：~634 令牌
  Webhook 处理：    ~344 令牌
  结账路由：       ~257 令牌
  Stripe 客户端：  ~33 令牌

每次会话合计：~1200 令牌
10 次会话合计：~12000 令牌浪费
```

### 令牌解法（已验证）

使用 memory-bank，同样会话开始约 ~400 令牌：

```
加载 MEMORY.md（紧凑格式）：  ~334 令牌
  整个项目上下文在一个结构化文件中
  决策、文件、状态、阻塞、架构

Claude 问候 + 用户确认：      ~60 令牌
  Claude 已掌握信息，无需多问

所需文件读取：                0 令牌
  记忆中有文件用途，不必读源码

每次会话合计：~394 令牌（约省 67%）
10 次会话合计：~3940 令牌（约省 ~8060）
```

数字基于示例文件用 tiktoken 测量。实际节省随项目复杂度变化（越大通常省得越多）。

### 渐进式加载

不要一次性把所有内容塞进上下文。分级加载：

```
第 1 级：始终加载（约 ~200 令牌）
  └─ 项目概览（1–2 句）
  └─ 上次停在哪（当前任务、状态、下一步）
  └─ 活跃阻塞

第 2 级：按需加载（需要时约 ~300 令牌）
  └─ 关键决策（仅当涉及决策时）
  └─ 关键文件（仅当处理第 1 级未涵盖的文件时）
  └─ 架构备注（仅当动到架构时）

第 3 级：仅在被问及时加载（需要时约 ~200 令牌）
  └─ 会话日志（仅速度与历史类问题）
  └─ 用户偏好（仅首次会话或相关时）
  └─ 外部上下文（仅处理 API/服务时）
```

**效果：** 不是一次加载 ~800 令牌的整份记忆，而是先加载 ~200，其余真正需要再加载。多数会话根本不需要第 3 级。

### 紧凑编码规则

`MEMORY.md` 每一行都针对「单位令牌信息量」优化：

**用结构化简写，不用散文：**
```
差（38 令牌）：
  「我们决定用 Prisma 做 ORM 而不是 Drizzle，因为 TypeScript 类型推断更好，
   而且团队在之前项目里已经熟悉它。」

好（14 令牌）：
  | 2025-04-01 | Prisma 优于 Drizzle | 类型推断、团队熟悉度 | 全部 DB |
```

**结构化数据用表格（压缩效果好）：**
```
差（分散散文 — 5 个文件约 120 令牌）：
  主结账路由在 src/app/api/checkout/route.ts。Stripe 客户端在...

好（表格 — 5 个文件约 60 令牌）：
  | 文件 | 用途 |
  | src/app/api/checkout/route.ts | 创建 Stripe 结账会话 |
  | src/lib/stripe.ts | Stripe 客户端单例 |
  | src/stores/cart.ts | Zustand 购物车 + 持久化 |
```

**进行中工作用清单（可扫读、信息密度高）：**
```
差（散文）：
  我们正在做 webhook 处理，部分完成。还要写测试，还没开始。

好（清单）：
  - [x] Stripe webhook — handlePaymentSuccess()
  - [ ] handleRefund() — 仍是桩，需实现
  - [ ] webhook 端点集成测试
```

**一行一个事实，无废话：**
```
差：「这个项目本质上是一个为……而构建的 Web 应用」
好：「烘焙电商。Next.js 14、Prisma、Stripe。四月上线。」
```

### 上下文预算跟踪

监控令牌使用，在撞上限前提醒：

```
会话开始时估算上下文预算：

可用上下文：   ~200000 令牌（Claude 窗口）
记忆加载：     ~800 令牌（第 1 级 + 已加载的更高级）
系统提示：     ~2000 令牌
剩余用于工作： ~197200 令牌

用量达 40%（约已消耗 80000 令牌）：
  → 建议：「上下文已用约 40%，可考虑尽快压缩。」

用量达 60%（约 120000 令牌）：
  → 自动保存会话检查点
  → 建议：「上下文约 60%，适合 /compact 或开新会话。」

用量达 80%（约 160000 令牌）：
  → 自动将完整状态写入 MEMORY.md
  → 提醒：「上下文约 80%，正在保存状态 — 可无损失在新会话继续。
     说「收尾」或继续当前会话均可。」
```

### 会话接续协议

当会话撞到上下文上限或用户想新开会话时：

```
步骤 1：紧急保存（在上下文耗尽前）
  └─ 将本会话一切写入 MEMORY.md
  └─ 写明精确光标位置：文件、函数、行号
  └─ 写明任何未提交的「心智模型」（Claude 当时的推理）
  └─ 写明半成品状态：已完成、一半完成、下一步

步骤 2：写入 CONTINUATION.md（一次性预热文件）
  └─ 极紧凑：少于 50 行、少于 500 令牌
  └─ 只含下一会话需要立刻开工的内容
  └─ 格式示例：

  ```markdown
  # 接续：[任务名]
  从 `src/auth/refresh.ts:47` 继续 — 正在写 rotateToken()
  
  ## 状态
  - handlePaymentSuccess()：完成 ✓
  - handleRefund()：第 89 行仍为桩，需 Stripe refund.created 事件
  - 测试：未开始
  
  ## 上下文
  - Stripe webhook 签名在中间件第 12 行已校验
  - 使用 stripe.webhooks.constructEvent()，非手动 HMAC
  - 退款处理与支付处理同一模式
  
  ## 立即下一步
  在 src/api/webhooks/stripe/route.ts:89 实现 handleRefund()，
  使用 stripe.refund.created 载荷。模式：
  提取 refund.payment_intent → 查找订单 → 状态更新为 "refunded"
  ```

步骤 3：下一会话「问候即开工」
  └─ 先读 CONTINUATION.md（快速路径）
  └─ 仅在需要时读 MEMORY.md 获取完整上下文
  └─ 加载后删除 CONTINUATION.md
  └─ 立刻开始工作 — 不问问题、不预热
```

**触发语：**「保存状态」「上下文快用完了」「晚点再继续」「会话太长了」

### 按功能统计的令牌节省（已验证）

| 功能 | 如何节省 | 实测影响 |
|------|----------|----------|
| 结构化记忆 vs 重复解释 | 紧凑文件替代 4+ 轮对话 | ~566 令牌/会话 |
| 取消「认路」式读文件 | 不必读源码即可理解项目 | ~634 令牌/会话 |
| 紧凑编码（表格优于散文） | 同样信息，比散文少 39–42% 令牌 | 记忆体积少 39–42% |
| 会话接续协议 | CONTINUATION.md 低于 200 令牌 vs 完整重预热 | 会话交接约省 ~1000 令牌 |
| 智能压缩 | 保持记忆在 150 行内 / ~700 令牌 | 防止长期膨胀 |

**合计验证（tiktoken 测量）：**

| 场景 | 令牌 | 轮次 |
|------|------|------|
| 无 memory-bank | ~1200/会话 | 8 轮 |
| 有 memory-bank | ~394/会话 | 2 轮 |
| **节省** | **~806/会话（约 67%）** | **省 6 轮** |
| 10 次会话 | **约省 ~8060** | 省 60 轮 |
| 30 次会话 | **约省 ~24180** | 省 180 轮 |

### 浪费令牌的反模式

**记忆文件中永远不要：**

```
✗ 能用表格却写冗长散文
✗ 在多个章节重复同一信息
✗ 在记忆里存代码片段（应写 文件:行 引用）
✗ 对已完成工作写长描述（仅一行摘要）
✗ 保留已解决的阻塞（应删除）
✗ 存储 README.md 或 CLAUDE.md 里已有的信息
✗ 用记忆存 Git 已跟踪的内容（提交历史、diff、blame）
```

**应当始终：**

```
✓ 结构化数据用表格（决策、文件、任务）
✓ 进行中工作用清单
✓ 项目概览一句话（不要一段）
✓ 用 文件:行 引用代替描述代码
✓ 删除已解决项（git 历史里仍有）
✓ 引用其他文件而非复制内容
```

> 完整令牌优化指南见 `references/context-efficiency.md`。

## 优秀记忆的规则

**要精确，不要模糊。**
差：「在做认证」  
好：「在 `src/auth/refresh.ts` 实现 JWT 刷新轮换 — `rotateToken()` 已完成，需在 `src/cache/tokens.ts:47` 补 Redis TTL 逻辑」

**「下一步（立即）」是最重要的一行。**  
应精确到 Claude 会话一开始就能写代码，零澄清问题。

**记录每个决策背后的「为什么」。**  
否则未来的 Claude 会再次面对相同权衡却无从依据。

**绝不存密钥。** 无 API key、密码、令牌或凭证。绝不，哪怕「临时」。应引用 `.env` 或密钥管理方案。

**会话结束整写，会话中途手术式更新。**  
会话结束 = 为一致性整文件重写。会话中途 = 只改相关节，避免丢失上下文。

**控制在 150 行以内。** 积极压缩。陈旧信息有害 — 误导大于帮助。

## 通过 CLAUDE.md 自动配置

若要全自动记忆与全部特性，在项目 `CLAUDE.md`（或全局 `~/.claude/CLAUDE.md`）中加入：

```markdown
## 记忆

每次会话开始时：
1. 检查项目根目录 MEMORY.md
2. 检查 ~/.claude/GLOBAL-MEMORY.md
3. 检查当前 git 分支及 .memory/branches/<分支>.md
4. 运行会话差异 — 自上次记忆更新以来有何变化
5. 为记忆健康度打分并标出问题
6. 用具体摘要与「下一步（立即）」问候我

会话过程中：
- 当我说「记住这个」或完成里程碑时更新记忆
- 在决策表中记录关键决策及理由

会话结束（当我说「收尾」「保存」「今天就到这」）时：
1. 写入全面的 MEMORY.md，反映完整当前状态
2. 确保「下一步（立即）」极其清楚
3. 超过 150 行则运行压缩
4. 确认已保存内容
```

> 完整集成指南见 `references/claude-md-integration.md`。
