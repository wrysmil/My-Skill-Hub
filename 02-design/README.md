# 📐 02-design — 定义方案，把需求变成可执行的图纸

> **要回答的问题：要解决这个问题，最小且正确的方案长什么样？**

## 什么时候进入

- 当你手里已经有可证伪的需求假设，需要回答"那要怎么做"的时候。
- 当你要决定系统的分层与架构模式，并且这个决定会影响后面几个月的改动成本的时候。
- 当实现方式需要别人评审、或者需要跨会话交接给另一个人 / 另一个 Agent 的时候。
- 当任务明显复杂、要跨越多次会话，靠脑子记进度已经不可靠的时候。
- 当你要做的是生产级界面，需要先把配色、排版、组件选型定下来的时候。

## 什么时候不该进入

- 需求还没验证 —— 方案再漂亮也是在给一个假问题设计架构，先回 `01-discover`。
- 你已经有一份完整的书面计划，现在要做的是执行它 —— 直接去 `03-build`。

## 产出物

- 一份实施计划，拆到"照着做不需要再做设计决策"的粒度，含阶段与检查点。
- 一份架构设计文档，说明分层、模块边界与技术选型理由，可直接给别人评审。
- 一份明确到可以交接的界面规格：配色、字体、组件与状态说明。
- 需要跨会话时，一份持续更新的 `task_plan.md`。

## 常见反模式

**「边写边想架构」** → 架构决策一旦写进代码就很难改，边写边定意味着你每次都在最贵的时刻做决定。

**「一次把架构设计到能支撑百万用户」** → 你还没有一百个用户，复杂架构本身就会拖慢验证速度，甚至直接让你做不完。

**「计划就是列一堆功能」** → 功能清单不是计划，计划要说明顺序、依赖、验收方式和出错时的退路。

**「UI 最后再美化」** → 界面是用户唯一能感知的部分，最后再补通常意味着推翻重做交互与数据结构。

## 下一步

当实施计划详细到可以直接照着写代码，进入 `03-build`。如果写计划的过程中发现需求本身站不住（比如核心场景依赖一个不存在的用户习惯），应该回退到 `01-discover` 重新验证，而不是靠设计技巧把它圆过去。
