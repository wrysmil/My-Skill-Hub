# 📄 90-docs — 交付物，技术之外的交付面

> **要回答的问题：怎么把技术成果变成别人能看懂、能拿走的东西？**

## 什么时候进入

- 当你的成果需要交给别人使用，而对方不会去读源码的时候。
- 当你要给非技术决策者汇报，需要一页纸说清结论与取舍的时候。
- 当交付形式明确要求 Word、PDF、PPT 或 Excel，而不是一个 md 文件的时候。
- 当你要把散落的知识整理成用户指南或内部知识库的时候。
- 当对方要求可编辑的源文件，而不是截图或导出的图片的时候。

## 什么时候不该进入

- 还没有可交付的成果 —— 文档不能替代实现，先把东西做出来。
- 受众就是你自己或同一个代码库里的开发者 —— 注释和 README 已经够了，不必为内部读者包装成正式文档。

## 产出物

- 一份可交付的技术文档或用户指南，别人照着能独立完成操作。
- 给非技术决策者看的一页纸：结论、依据、代价、需要他做的决定。
- 数据表：可编辑、带公式、口径与来源写清楚。
- 需要时，一份演示文稿或可填写的 PDF 表单。

## 技能

| 技能 | 什么时候用它 |
| --- | --- |
| [`technical-writer`](technical-writer/) | 要写技术文档、用户指南、知识库时 |
| [`docx`](docx/) | 交付物要求 Word 文档，或需要格式与批注处理时 |
| [`pdf`](pdf/) | 涉及 PDF 读取、合并、拆分或表单处理时 |
| [`pptx`](pptx/) | 涉及演示文稿生成与编辑时 |
| [`xlsx`](xlsx/) | 涉及表格数据、公式与图表时 |

## 常见反模式

**「文档等有空再写」** → 交付前的时间总是最紧，等到"有空"通常意味着最后交出去的是没有说明的半成品。

**「给老板看的东西把代码细节都贴上去」** → 决策者要的是结论和代价，代码细节只会让他抓不住重点，反而更不敢拍板。

**「用截图代替可编辑的源文件」** → 截图无法修改、无法搜索、无法复用，对方要改一个字都得回来找你。

**「一份文档写给所有读者」** → 开发者、用户、决策者关心的东西完全不同，混在一起写等于谁都没服务好。

## 下一步

交付物不推动流程前进，它随时可以被调用：每个阶段结束、每次需要把成果交给别人时，都可以回到 90-docs。写完文档后如果发现自己讲不清某个结论的依据，那通常说明该回到对应的主线阶段补证据，而不是靠文字把它圆过去。
